# 用户 / GPT / Codex / GitHub 协作与审核协议

## 1. 职责

| 角色 | 负责 | 不负责/不自动拥有 |
|---|---|---|
| 用户/项目负责人 | 资源许可、范围与最终选择、课程提交、AI辅助披露 | 不被要求手动替代每次代码测试 |
| GPT reviewer | 方案审查、代码/证据审计、科学门禁、结论边界、审核记录 | 不假装已经运行未运行的实验；不承诺后台持续监控 |
| Codex executor | 安装与实现、测试、真实运行、故障定位、artifact、PR和交付 | 不自签GPT批准，不改测试答案，不自行扩大训练/实机范围 |
| GitHub | 版本、issue、PR、协议、review和公开结果的记录系统 | 不自动成为GPU平台或Codex任务调度器 |

一个GitHub账号可能承载多个工具提交。角色分离是明确的工作流与证据来源区分，不是密码学身份隔离。GitHub若不允许同账号approve其自己的PR，使用绑定SHA的审核文件/评论并由用户合并，不伪造独立reviewer账号。

## 2. 信息优先级

用户最新明确决定 > 已签署且绑定协议/提交的最新适用审核决议 > 冻结protocol/config > 当前计划 > 历史讨论。发现冲突必须记入issue，不能在多个版本中挑最方便的一条。

`docs/STATUS.md` 是状态索引，不是单独的实验事实来源。每个PASS和授权必须链接具体review、PR/commit或运行证据。历史审核文件不可覆写，只能新增superseding记录。

## 3. Git与PR流程

1. 从最新main建 `codex/<issue-number>-<scope>`。
2. 实现当前工作包；先提交代码，再执行需要固定身份的实验。
3. PR描述变更、实际运行命令、通过/失败/未运行、artifact与科学影响。
4. 同步执行issue和阶段报告。Codex self-check状态为 `READY_FOR_REVIEW`。
5. 用户在对话中提供PR/issue，或在实际可用的审核触发流程中请求GPT审查；GPT读取实时仓库/证据后出具结论。
6. 审核绑定确切head SHA；新提交使旧代码审核需复核，除非决定中明确只涉及不改变结论的文档修正。
7. 用户或明确获授权的reviewer合并；不由执行者自行以“测试已过”代替审核。

初始文档bootstrap由用户明确要求直接推送main；后续实现采用PR。分支保护、自动化任务、CI执行权限本次未修改，文档约定不等于服务端强制规则。

## 4. 三个实质关口

| 关口 | 需要审核 | 可放行内容 |
|---|---|---|
| R1：原生运行资格 | M0资源/版本；M1真实推理、接口、完整episode、重复正常成功、成本 | M2–M3 shadow、oracle、Gate和校准 |
| R2：实验冻结 | shadow无副作用；非循环标签；Gate真拦截；split；阈值/条件/统计/预算冻结 | M4正式TEST |
| R3：结果与提交 | 全部计划cell、指标计算、缺失/失败、置信区间、claim-evidence、复现 | 最终提交包 |

日常小修复、CPU测试和授权范围内收集证据可继续，不把每个函数变成人工审批。重大范围、预算、阈值/标签或数据split变化才需change request。

## 5. Reviewer结论枚举

- `APPROVED_FOR_NEXT_STAGE`：明确通过项、下一阶段范围与预算。
- `CONDITIONAL_APPROVAL`：列出必须机器可检验/可核实的前置条件，完成前不能越过相应边界。
- `CHANGES_REQUIRED`：列出阻塞、复核证据与允许继续的工作。
- `BLOCKED_RESOURCE`：缺资源/访问，不能假装科学失败。
- `PROTOCOL_REVISION_REQUIRED`：科学定义或范围发生变化，创建新版本。
- `READY_FOR_SUBMISSION`：只表示项目审查通过，不代替教师评分或课程政策许可。

每份review注明：作者角色、日期、protocol_id、审阅commit/PR、实际读取/运行了什么、未验证什么、证据链接、问题严重性、决定和下一步。

## 6. 必须阻塞的情形

真实模型被mock替代却不标注；格式检查通过被当作成功episode；Gate拒绝后仍执行候选；检查/执行不一致；shadow改动主状态或随机流；oracle读取risk答案；看TEST调阈值；失败样本消失；无完整版本身份；无违规事件却声称UAR=0；结果截图无可复算数据。

局限如“仅仿真”“特权状态”“样本小”不必自动否决，但必须进入最终结论边界。

## 7. Change Request

记录原要求、拟改项、证据、必要性、影响哪些既有run、是否需重跑、预算和新的claim边界。示例：改hold/replan、换任务/权重、调整oracle、扩大prediction horizon、增加训练或改测试样本。

禁止用“工程修复”名义悄悄改变科学问题。真正的bug修复也须说明受影响结果和重跑范围。

## 8. 证据组织

建议目录：`reports/<milestone>/`、`results/<protocol_id>/`、`docs/reviews/`、`docs/decisions/`。原始大文件用清单绑定，公开摘要不能代替审查所需原始证据；访问不到时review写 `NOT_VERIFIED`。

每次交接必须回答：做了什么、以哪个SHA运行、实际结果是什么、失败是什么、原始证据在哪里、还有什么没做、希望批准哪一段。不能仅发“全部完成，请验收”。

## 9. 首轮授权

R000仅批准范围和M0–M1有界启动，不批准任何实验有效性。执行总预算<=24开发episode，无训练、无正式TEST、无实机、无WBC、无停止他人任务。实际资源使用仍需现有授权成立。

本协议不创建持续运行的GPT任务，不自动启动Codex。完成一个交接后，需要真实提交/审核动作才能进入下一关。
